### <a name="_qmphm5d6rvi3"></a>**Решение**
Использованием CQRS (Command Query Responsibility Segregation).
Будет создан новый сервис OrderHistory (Сервис Истории Заказов).
Этот сервис будет иметь свою собственную, оптимизированную для чтения базу данных (например, PostgreSQL с денормализованной таблицей Orders_ReadModel).
Он подпишется на все события в Kafka, касающиеся жизненного цикла заказа.
При получении события OrderHistory обновляет свою локальную денормализованную запись о заказе.
Мобильное приложение покупателя будет обращаться к API-шлюзу, который перенаправит запрос напрямую в сервис OrderHistory.


### <a name="_bjrr7veeh80c"></a>**Альтернативы**
1. API Composition (Композиция на уровне API Gateway или нового сервиса)
Описание: Создать новый "композитный" сервис или использовать API-шлюз для сбора данных из всех участвующих микросервисов в реальном времени при каждом запросе истории заказов. Сервис истории заказов делал бы REST-запросы к OrderService (получить список ID заказов), затем к PaymentGateway (получить статус оплаты), DeliveryProvider (получить статус доставки) и т.д.
Плюсы: Простота реализации на начальном этапе, не требует новых компонентов хранения данных, данные всегда актуальны (eventually consistent не требуется).
Минусы: Высокая задержка (latency) из-за множества сетевых вызовов (round-trips) при каждом запросе; сильная связанность между сервисами (если один сервис падает, история покупок не отображается); высокая нагрузка на внутренние сервисы чтения. Не соответствует требованию высокой скорости отклика.
2. Event Sourcing (ES)
Описание: Хранить каждый заказ как последовательность неизменяемых событий (OrderPlaced, ItemAdded, PaymentSucceded, Delivered). Текущее состояние заказа восстанавливается путем "проигрывания" этих событий.
Плюсы: Точное логирование всех изменений, высокая согласованность данных.
Минусы: Очень высокая сложность реализации и поддержки, требует специализированных баз данных (Event Store), сложность в отладке и создании сложных запросов (приходится совмещать с CQRS для чтения). Избыточно для текущей задачи.

**Недостатки, ограничения, риски**

Появление рассогласования данных (eventual consistency) — статус может обновиться в интерфейсе покупателя с небольшой задержкой (секунды); усложнение архитектуры (новый сервис, новая БД для чтения, логика синхронизации).
